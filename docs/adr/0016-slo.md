# ADR-0016: SLO values

**Status:** Accepted

## Context
I need SLOs for the store: a target for each SLI from ADR-0015, and alert thresholds. The numbers should come from something I measured, not from nowhere.

What I have from M3 YCSB in AWS (16 threads, workload A, W=2 R=2): read p99 3-6 ms, write p99 31-41 ms, 1-2 failed reads of ~25 000. Writes are slow because every write is an fsync on the leader (M3 benchmark).

## Options
1. **Strict SLOs** (like p99 < 10 ms for everything) - writes already break this under the benchmark load, the alert would fire all the time.
2. **SLOs from my measurements with some room** - the system meets them under the benchmark load, and an alert means something really changed.
3. **No latency SLO, only availability** - simple, but M5 autoscaling needs a latency target.

## Decision
Option 2. Measured on the coordinator, over 5 minutes:

| SLI | SLO | Where the number comes from |
|---|---|---|
| Availability | 99.5% of item requests are not `5xx` | M3 had ~0.01% failed reads; 99.5% leaves room for a follower restart, when W=3 / R=3 requests get `503` |
| Read latency | p99 < 20 ms | measured 3-6 ms, x3 for room |
| Write latency | p99 < 100 ms | measured 31-41 ms, x2.5 for room |

Alerts:
- **High latency:** read p99 > 20 ms or write p99 > 100 ms for 2 minutes.
- **Node down:** a target is not scraped (`up == 0`) for 30 s, or a shard has fewer than 3 alive replicas.
- **Replication lag:** > 5 s for 30 s. Normally lag is under a second (long poll returns at once on a new write).

## Consequences
- (+) An alert means something changed compared to the system I measured.
- (+) M5 can scale on the same p99 threshold.
- (-) The numbers are from one benchmark run on t3.micro. If the load changes, the SLOs need a new look.
- (-) 99.5% is measured over short sandbox sessions, not over a month like a real SLO.

**Where it lives:** `monitoring/alerts.yml`, the dashboard in `monitoring/grafana/`
