# M5 - AI design review

I gave an AI chat my M5 proposal, ADR-0020..0022, the migration code, the routing and registration part of the coordinator, the new replica endpoints, the wal / ring changes, the autoscaler, the ops MCP server and the `ShardCount` part of the template, and asked it to critique the design. The prompt and the answer are in `ai-review-transcript.md`.

It found 28 points. I checked each one against the code before deciding. Two were real bugs that I reproduced with tests: a retried import batch answered `200` without W acks (point 3), and the autoscaler counted "no data" as "idle" and would drain shard-2 under load (point 10).

## My decisions

| # | AI point | Decision | Why | Change |
|---|---|---|---|---|
| 1 | **3** A retried import or purge batch returns `200` without quorum, and then the old shard purges (HIGH) | **Accept** | Reproduced: the first try writes and times out, the retry skips everything and answers `200` with nothing confirmed. | The leader always waits for W acks up to the end of its log, even when nothing new was written. Test `TestRetriedImportStillWaitsForW` |
| 2 | **10, 11** Missing data counts as "low"; failed writes are not in p99 (HIGH) | **Accept** | True: `5xx` are left out of the histogram (ADR-0016), so if every write fails p99 is empty while traffic is high, and that looked like an idle store. | New "no data" state: coordinator not `up`, or traffic but no p99 - both timers reset, no action. More than 1% failed writes for 2 min also scales up. Tests `TestNoDataIsNotIdle`, `TestErrorsScaleUp`, ADR-0020 |
| 3 | **1** The switch is not a fence: writes that started before it can land on the old shard after the floor or after the dump (HIGH) | **Accept (my own fix)** | True, the 5 s grace was a guess. I don't pause writes like the AI suggests - it can be done with what is there. | Grace (10 s) is twice the coordinator timeout to a shard (5 s), so every write with a `200` is done before the dump. The floor is the old max version **plus the grace time**, so a new write on the new owner always wins over that window. After the purge the old shard is dumped again and late moved keys (their client already got an error) are purged too. Test `TestLateWriteOnTheOldShardIsDropped`, ADR-0021 |
| 4 | **6** A shard joins when only its leader has registered, so W=2 writes fail (HIGH) | **Accept** | True: `join` only checked the leader, and the three instances boot at different speeds. | A new shard goes on the ring only when all 3 replicas are alive. Test `TestJoinWaitsForAllReplicas` |
| 5 | **12** Scaling down on low p99 flaps: p99 on 2 shards doesn't say what it will be on 1 (HIGH) | **Accept** | True for a steady medium load. | Scale down also needs less than 100 writes/s (`--down-rate`). 100 is a first guess, I check it in the slow-growth run. Test `TestBusyStoreDoesNotScaleDown` |
| 6 | **20, 21, 22, 23, 24** Ops agent: Claude Desktop also has the M4 `kvstore` server with `delete_item`; `opsmcp` holds the admin token; free text in alerts; heavy PromQL; different traffic query; REBALANCE not defined | **Accept** | All true and cheap. | `opsmcp` needs no token (`/health` now has the move state); no annotation text in `get_alerts`; 5 s query timeout; the agent uses the same write-only queries as the autoscaler; REBALANCE = stuck move or ring vs `ShardCount` mismatch, done by a human. For the ops chat the `kvstore` server is off. After the AWS run the rules are also in the `get_cluster` description, because Claude Desktop ignored the `initialize` instructions. ADR-0022, `docs/m5/ops-agent.md` |
| 7 | **7** Registration accepts any shard ID (HIGH) | **Accept (partly)** | An accident like starting a shard with the wrong `SHARD_ID` would start a move. A registration token is not needed: port 9080 is open only to the shard and monitoring security groups (ADR-0019). | `ALLOWED_SHARDS=shard-1,shard-2`, others get `403`; on an empty ring only a shard from `EXPECTED_SHARDS` can be first. Test `TestOnlyAllowedShardsRegister` |
| 8 | **4** One fsync per imported or purged item | **Accept** | True, and the purge runs on the shard that is already overloaded. | Import and purge are one log write per batch of 500. The "low" points next to it are already fine: followers apply purges and imports with the same version check (`store.Apply`, `store.Purge`). |
| 9 | **9** A failed fallback read returns `404` for a key that exists | **Accept** | True, "not found" is worse than an error. | `503` when the old shard doesn't answer |
| 10 | **13** 60 ms is between the 50 and 100 ms buckets | **Accept (partly)** | True. I don't raise the minimum traffic to 20 writes/s: p99 has to stay above 60 ms on every check for 2 minutes, one slow fsync doesn't do that. | Bucket at 60 ms added (20 ms was already there) |
| 11 | **2** `Import` doesn't move the version counter; the floor is not saved | **Refute (partly)** | The first part is not true: `Log.write` sets `version = max(version, e.Version)` for every entry, imported ones too. The floor lives only in memory, true - but if the new leader restarts during a move, the shard is down anyway (no failover, ADR-0011) and the move has to be restarted by hand. | ADR-0021 minus |
| 12 | **5** Ring and `removed` live only in RAM | **Refute (partly)** | Scaling doesn't restart the coordinator: I checked that `ShardCount` changes only `Shard2A/B/C`. After a normal restart the ring rebuilds from heartbeats: shard-1 first (fixed now, see 7), then shard-2 joins with a move that copies nothing wrong. The left-over risk is a coordinator restart in the minute between a drain and the stack update. | ADR-0021 minus |
| 13 | **8** Retries never give up, no abort | **Refute** | With a fixed leader and no failover (M3), if a leader dies its shard is down anyway; the move just waits for it. An abort is more code than the milestone asks. | ADR-0021 minus |
| 14 | **15, 16** Cooldown starts at the decision; no timeout on the drain wait; stack and ring can disagree | **Accept (partly)** | Cooldown and timeout are cheap. The mismatch only happens after a crash of the autoscaler; that is the REBALANCE case for a human. | Cooldown starts after the action is done, drain wait has a 15 min timeout |
| 15 | **17** Scale up takes 4-6 min; use stopped instances as a warm standby | **Refute** | Start/stop needs the shard to wipe its data on `410` and more autoscaler code. I keep CloudFormation and say honestly that a short spike is over before the new shard helps. | ADR-0020: 4-6 min |
| 16 | **18** The stack is complete before the shard works; the presigned URL is old after a session restart | **Refute** | Links are valid for 4 h and a session is 3 h; every session starts with a fresh deploy from the pipeline. The autoscaler doesn't trust the stack, it looks at the ring. | - |
| 17 | **19** `ShardCount` can change other resources (coordinator, monitoring) | **Refute** | Checked: only `Shard2A/B/C` have `Condition: TwoShards`, and Prometheus gets the replicas from the coordinator (HTTP SD, M4). | - |
| 18 | **25** gp2 burst credits will run out; use gp3 | **Refute** | The sandbox allows only gp2. I note it as a risk for the long run. | `docs/m5/benchmark.md` |
| 19 | **26, 27** Run YCSB inside the VPC; write a correctness checker | **Refute** | YCSB runs from CloudShell like in M2 and M3, so the numbers can be compared. Writes and deletes during a move are checked by `TestReadsAndWritesDuringTheMove` and `TestLateWriteOnTheOldShardIsDropped`. | - |
| 20 | **14** Check that a new shard would help (CPU, coordinator) | **Refute** | The M3 benchmark showed the bottleneck is the fsync queue on the shard leader. More checks in the autoscaler are more than the task asks. | - |
| 21 | **28** What the benchmark can and can't show; 1 shard at idle is below M2 | **Accept (docs)** | Fair. | `docs/m5/benchmark.md`, ADR-0020 |
| 22 | **Low** `startMigration` panics if the group is missing | **Accept** | True. | Returns an error |
